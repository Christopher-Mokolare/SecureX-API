1. Unblocked — Can Be Built Now

1.1 Seller Bank Details Collection 🖥⚙️ Both

What's missing

There is no way for a seller to submit their banking information. The User model already has BankAccountNumber, BankBranchCode, and BankGroupId fields in the database, but there is no API endpoint or UI form to collect these values.

Why it matters

When a buyer accepts an item and the deal is marked Completed, the system automatically triggers a payout to the seller via Ozow. If the seller has no bank details on record, the payout is silently skipped with a warning log. No money reaches the seller.

What needs to be built
  • ⚙️ BE — POST /api/users/{id}/bank-details endpoint for sellers to submit bank account number, branch code, and Ozow bank group ID
  • ⚙️ BE — GET /getavailablebanks proxy or cached list so the frontend can show a bank picker
  • 🖥 FE — A form or screen where the seller fills in their banking details after the deal is created
  • 🖥 FE — Bank dropdown populated from the Ozow banks list so the correct BankGroupId is submitted

1.2 Dispute Resolution Endpoint ⚙️ Backend

What's missing

The endpoint POST /api/transactions/{id}/resolve-dispute does not exist yet.

Why it matters

When a buyer rejects an item within the 24-hour inspection window, the transaction moves to RequiresRefund status. Funds are held in the Ozow float and neither party receives anything. There is currently no way to resolve this — no admin can decide the outcome, and no refund or payout can be triggered.

What needs to be built
  • ⚙️ BE — POST /api/transactions/{id}/resolve-dispute admin endpoint accepting { decision: "release-to-seller" | "refund-to-buyer" }
  • ⚙️ BE — If release-to-seller: call OzowPayoutService.RequestPayoutAsync with seller bank details
  • ⚙️ BE — If refund-to-buyer: trigger refund mechanism (depends on decision in Section 3.1)

1.3 Deploy C# API to Render ⚙️ Backend

What's missing

The live URL https://securex-btit.onrender.com is currently running the old Node.js webhook service, not the new C# ASP.NET Core 8 API.

Why it matters

All new functionality — deal creation, state machine, KYC, payout triggering, audit logs — lives in the C# API. The frontend and Ozow webhooks point at the Render URL, but the C# API has never been deployed there.

What needs to be done
  • ⚙️ BE — Add a Dockerfile or configure Render to build and run the C# project from SecureX.Api/
  • ⚙️ BE — Set all environment variables on Render (database URL, Ozow keys, JWT secret, etc.)
  • ⚙️ BE — Verify the health endpoint GET /health returns 200 after deploy
  • ⚙️ BE — Decommission the old Node.js service once confirmed working

2. Blocked on Ozow

2.1 Payout API Activation ⚙️ Backend

What's missing

The Ozow Payouts API (stagingpayoutsapi.ozow.com) is returning 403 Missing Authentication Token for all requests. The merchant account SECUREXPTYLTD (site code SEC-SEC-014) has not been activated for payout access on the staging environment.

Why it matters

Until this is resolved, no staging payout tests can be run and the end-to-end payout flow cannot be verified.

What needs to happen
  • ⚙️ BE — Ozow support must manually activate payout access and provide a Payout API Key — email sent to support@ozow.com, awaiting response

2.2 Ozow Staging Test Cases ⚙️ Backend

What's missing

Ozow requires merchants to complete mandatory staging test scenarios before granting production access. These cover: successful payout flow, verification webhook returning isVerified: false, account number decryption failure, and payout cancellation.

Why it matters

Without passing these tests, Ozow will not grant production payout access. No live payouts can happen.

What needs to happen
  • ⚙️ BE — Once payout API access is activated (2.1 above), run and pass all required Ozow staging test scenarios

2.3 Ozow Float API for Reconciliation ⚙️ Backend

What's missing

The daily reconciliation service runs at 02:00 SAST and compares the expected float (sum of all FundsSecured transactions) against the actual Ozow float balance. The Ozow float fetch is currently stubbed and always returns 0.

Why it matters

Without the real float balance, the reconciliation service cannot detect discrepancies between what SecureX expects to hold and what Ozow actually holds.

What needs to happen
  • ⚙️ BE — Ozow (Teyla) to provide the float balance API endpoint
  • ⚙️ BE — Replace the stubbed return 0 in ReconciliationService with a real API call

3. Blocked on Business Decisions (Karabo)

3.1 Refund Flow — How Does the Buyer Get Their Money Back? 🖥⚙️ Both

What's missing

When a dispute is resolved in the buyer's favour, the funds are sitting in the Ozow float. There is no implemented mechanism to return those funds to the buyer.

Why it matters

Without a refund mechanism, buyers who reject an item are left with no recourse. Funds are stuck in the float indefinitely.

Decision needed from Karabo
  • Does Ozow support a direct refund from the float back to the buyer's original payment method? If yes, what is the API call?
  • Or does SecureX manually EFT the buyer from the business account?
Once decided
  • ⚙️ BE — Implement the refund call in the dispute resolution endpoint
  • 🖥 FE — Show the buyer a refund confirmation screen with expected timeline

3.2 Payout Routing — Seller Account or SecureX Business Account? ⚙️ Backend

What's missing

When a deal completes, the payout currently goes directly to the seller's personal bank account. It is unclear whether this is the intended flow or whether funds should first land in the SecureX business account.

Why it matters

This determines what bank details are used in the Ozow payout request and whether SecureX acts as a pass-through or holds funds first.

Decision needed from Karabo
  • Does the payout go directly to the seller's bank account via Ozow?
  • Or does it go to the SecureX Capitec Business account (1055374116) first?
Once decided
  • ⚙️ BE — Update TriggerPayoutAsync to use the correct destination bank details

3.3 KYC Provider — ThisIsMe / SmileID 🖥⚙️ Both

What's missing

The KYC state machine is fully wired up. When POST /api/transactions/{id}/start-buyer-kyc is called, the transaction moves to BuyerKycPending. However, no actual KYC session is initiated — the system never calls SmileID or ThisIsMe.

Why it matters

Without real KYC, there is no identity verification on buyers or sellers. This is a compliance and fraud risk.

What needs to happen
  • ⚙️ BE — Karabo to provide ThisIsMe or SmileID API credentials and documentation
  • ⚙️ BE — Update start-buyer-kyc to call the KYC provider and return a session URL or SDK token
  • ⚙️ BE — Update kyc-webhook to handle the real provider's callback format
  • 🖥 FE — Frontend to redirect the user to the KYC session URL or embed the SDK

3.4 Communications — Email and WhatsApp Notifications ⚙️ Backend

What's missing

There are no notifications of any kind. Buyers and sellers receive no emails or WhatsApp messages at any point in the deal lifecycle.

Why it matters

Without notifications, users have no visibility into what is happening with their deal. This will result in support queries and loss of trust.
